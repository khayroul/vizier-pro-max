## 1. Overview

Combined spec for Gate 2 ("Works While I Sleep") and Gate 3 ("Builds Itself"). Structured as Sequential Layers: Gate 2 builds a stable platform, Gate 3 extends it with self-building capabilities.

**Gate 2 delivers:** All 8 workflow toolsets, pre-session classification, parallel sessions, unattended cron, OpenSpace skill capture, DreamSkill memory consolidation, quality gate layers 3-6, Telegram/WhatsApp delivery.

**Gate 3 delivers:** DSPy distillation (GPT-5.4-mini -> Qwen local), code workflow with tiered autonomy, execute_code sandbox extensions, data-driven triggers.

**Revenue rule:** Gate 2 must produce billable unattended output before Gate 3 begins.

### Key Decisions (from brainstorming + senior review)

| Decision | Resolution | Rationale |
|----------|-----------|-----------|
| Toolset switching | Pre-classify with Qwen, no mid-session switch | Hermes `/tools enable\|disable` resets session context. Not acceptable for interactive use. |
| Fallback strategy | vizier-fallback (all tools, ~44KB) for uncertain classification | `describe_tools` + session reset is worse UX than the 44KB token cost. 10% of sessions x 44KB = ~4.4KB amortized. Irrelevant with free 10M tokens/day. |
| OpenSpace mode | Hermes lifecycle hooks (plugin) | Reactive observation fits hooks. Same pattern as prompt_logger. Simpler than MCP server. |
| Sandbox | Permissive + audit (Gate 3) | Allow installed imports, restrict filesystem/network, log everything. Tighten in Gate 4 based on data. |
| Distillation goal | Cost reduction AND offline capability | Dual purpose. Incremental: one task type at a time. |
| Self-building autonomy | Tiered: auto-promote collapses, human-approve new tools | Balances speed with safety. |
| LLM in pipelines | Allowed when self-contained. | Pipelines MAY include LLM calls for full brief→deliverable flows. Simplifies orchestration vs forcing model to chain 3-4 tool calls. Revised from original "never" rule after Gate 1+2 hardening validated the self-contained pattern. |
| Complex deliverables | Model orchestrates (Gate 2), auto-collapse to meta-pipelines (Gate 3) | DAG execution lives in model + delegate_task, not in pipeline code. |
| Task decomposition | Model decomposes directly, no task_decomposer module | Model understands task dependencies better than regex. Patterns in SOUL.md instead. |

### Supersedes Parent Spec

The following decisions in this spec override the original architecture spec (`2026-04-01-vizier-pro-max-design.md`):

| Parent Spec Reference | Original Decision | Override | Rationale |
|-----------------------|-------------------|----------|-----------|
| Section 5.1, 12 | `switch_toolset` meta-tool via Hermes patch in Gate 2 | Pre-classify + vizier-fallback. No mid-session switch. | Hermes `/tools enable\|disable` resets session (loses context). Pre-classify is cheaper and simpler. |

## 2. Gate 1 Hardening — Reconciliation with Production

Gate 1 and Gate 2 hardening (commits `a19606a`, `3de93ff`, `e114998`) applied 49+ fixes including security, reliability, correctness, and observability improvements. This section reconciles the original spec proposals with what was actually built.

### 2.1 Pipeline Architecture (REVISED)

**Original spec:** Pipelines must be purely mechanical. No LLM calls inside pipelines. Rename `brief` to `content`.

**Production reality:** `content_generate.py` accepts `brief` and handles the full flow internally: RAG retrieval via LightRAG → LLM generation via `llm_chat()` → formatting → PDF rendering. Other pipelines (`competitive_analysis`, `poster_batch`) follow the same self-contained pattern.

**Revised principle:** Pipelines MAY include LLM calls when the full flow is self-contained. This simplifies model orchestration — one `run_pipeline` call instead of 3-4 chained tool calls with model reasoning between each. The three-layer model becomes:

```
Layer 1 (pipelines)  = self-contained workflows, may include LLM + mechanical steps
Layer 2 (atomic tools) = individual operations
Layer 3 (improvisation) = execute_code for novel tasks
```

**No changes to `content_generate.py` or `_registry.yaml`.** The `brief` input contract is correct for a self-contained pipeline that generates content from a brief.

### 2.2 RetryConfig (KEEP)

**Original spec:** Remove dead code.

**Production reality:** `RetryConfig` exists in `adapter/schemas.py` (frozen Pydantic model, lines 40-46). Executor doesn't use it, but manifests may declare `retry:` fields. Removing it could break YAML parsing.

**Decision:** Leave as-is. Harmless frozen schema. If delivery retry is needed later, the schema is already in place.

### 2.3 Executor Output Limits (STILL NEEDED)

**Status:** Not yet implemented. Input limits exist (query tools clamped to [1, 1000]) but subprocess stdout/stderr has no cap.

**Fix:** Cap subprocess output at 1MB in `adapter/executor.py`. Truncate with `[TRUNCATED: output exceeded 1MB limit]` marker. This is the **only remaining Section 2 fix** — safe to add, no conflict with existing hardening.

### 2.4 CLI Argument Safety (ALREADY DONE)

**Status:** Applied at Gate 1 hardening (commit `a19606a`). Line 92 of `executor.py`: `safe_args = {k: shlex.quote(str(v)) for k, v in args.items()}`. Subprocess uses `shell=False`.

**No changes needed.**

### 2.5 What Gate 1+2 Hardening Already Fixed

For reference, major hardening fixes that are now part of the production baseline:

| Category | Fixes | Scope |
|----------|-------|-------|
| Security | CLI injection (shlex.quote), SSRF protection, template RCE (SandboxedEnvironment), path traversal, FFmpeg injection, Pandoc injection | 8 critical fixes |

## 3. Session Lifecycle & Entry Points (Gate 2)

### 3.1 Message Flow

```
Message arrives (Telegram / API / CLI)
  -> Entry point receives raw text + metadata (chat_id, user_id, platform)
  -> pre_classify.py(message) -> {"toolset": "vizier-content", "confidence": 0.92}
  -> If confidence >= 0.8: toolsets = [classified_toolset]
     If confidence < 0.8:  toolsets = ["vizier-fallback"]
  -> Start Hermes session: hermes --toolsets {toolsets} --prompt {message}
  -> Hermes runs conversation (tools, pipelines, quality gate)
  -> Response returned to entry point
  -> Entry point delivers response via originating channel
  -> on_session_end hooks fire (OpenSpace, DreamSkill)
```

### 3.2 Entry Points

| Entry Point | Location | Framework | Trigger |
|-------------|----------|-----------|---------|
| Telegram bot | `entrypoints/telegram_bot.py` | python-telegram-bot polling loop | User message or file upload |
| API server | `entrypoints/api_server.py` | FastAPI | HTTP POST to /chat endpoint |
| CLI wrapper | `entrypoints/cli.py` | argparse | Terminal command |
| Cron scheduler | Hermes built-in (`cron/scheduler.py`) | File-locked timer | Schedule match |
| Data trigger | `scripts/triggers/data_trigger.py` | Filesystem polling | New file in uploads/ |

### 3.3 Telegram Bot Handler

```python
# entrypoints/telegram_bot.py (simplified)
async def handle_message(update: Update, context: ContextTypes.DEFAULT_TYPE) -> None:
    message = update.message.text
    chat_id = update.message.chat_id

    classification = pre_classify(message)
    toolsets = resolve_toolsets(classification)

    result = await run_hermes_session(
        prompt=message,

        metadata={"chat_id": chat_id, "platform": "telegram"},
```

## 4. Hermes Plugin Contract (Reference)

All plugins in this spec (OpenSpace, DreamSkill, Sandbox) use the Hermes v0.6.0 plugin system. This section documents the contract verified against source.

### 4.1 Plugin Structure

```
plugins/{name}/
  plugin.yaml     # name, description, hooks list
  __init__.py     # register(ctx) function
```

### 4.2 Available Hooks and Signatures

| Hook | When it fires | Arguments | Can block? |
|------|---------------|-----------|------------|
| `on_session_start` | Session begins | session_id, model, platform | No |
| `pre_llm_call` | Before each LLM API call | session_id, user_message, conversation_history, is_first_turn, model, platform | No |
| `post_llm_call` | After each LLM API call | session_id, user_message, assistant_response, conversation_history, model, platform | No |
| `pre_tool_call` | Before tool execution | tool_name, args, task_id | No (fire-and-forget) |
| `post_tool_call` | After tool execution | tool_name, args, result, task_id | No (fire-and-forget) |
| `on_session_end` | Session cleanup complete | session_id, completed, interrupted, model, platform | No |

### 4.3 Critical Constraint: Hooks Are Synchronous

**Hooks are called synchronously (`ret = cb(**kwargs)`, not awaited).** This means:

- Hooks CAN make synchronous HTTP calls (e.g., `httpx.post()` to Ollama)
- Hooks CANNOT use `async/await`
- Long-running hooks (DreamSkill's 2-5s Ollama call) will block the calling thread
- `on_session_end` fires AFTER session cleanup — blocking is acceptable (user is done)
- `post_tool_call` fires between tool calls — blocking delays the next tool call

### 4.4 Implications for This Spec

- **OpenSpace `post_tool_call`:** Must be fast (~5ms). Only records to SQLite. No analysis.
- **OpenSpace `on_session_end`:** Can take 100-500ms for pattern analysis. Acceptable.
- **DreamSkill `on_session_end`:** Takes 2-5s for Ollama call. Acceptable (user is done). Uses synchronous `httpx.post()` to Ollama, not async.
- **Sandbox `pre_tool_call`:** Must be fast (~10ms). AST scan only. No network calls.

## 6. Pre-Session Classification (Gate 2)

Qwen 3.5 9B (already pulled on Mac Mini M4, zero cost) classifies incoming tasks before the Hermes session starts.

### 6.1 Classification Flow

```
User message arrives (Telegram/API/CLI)
  -> pre_classify.py calls Ollama (Qwen 3.5 9B, ~10ms)
  -> Returns: {"toolset": "vizier-content", "confidence": 0.92}
  -> If confidence >= 0.8: start Hermes with that toolset
  -> If confidence < 0.8: start Hermes with vizier-fallback
  -> Hermes session begins
```

### 6.2 Classifier Script

Location: `scripts/routing/pre_classify.py`

- Input: raw user message (string)
- Output: `{"toolset": "vizier-content", "confidence": 0.92}`
- Method: Few-shot prompt to Qwen with structured output format. The model self-reports confidence (0.0-1.0) as part of the JSON response.
- Timeout: 5 seconds. If exceeded, default to vizier-fallback.
- Fallback: If Ollama is down, returns malformed JSON, or returns an unknown toolset name, default to vizier-fallback. All errors caught and logged.

### 6.3 Confidence Extraction

Qwen self-reports confidence via structured output. The prompt instructs:

```
Respond with ONLY a JSON object: {"toolset": "<name>", "confidence": <0.0-1.0>}
Confidence = how certain you are this is the right toolset.
If the task spans multiple workflows, return toolset "vizier-fallback" with confidence 0.95.
```

Self-reported confidence is not calibrated, but for routing purposes (binary decision: specific vs fallback), it's sufficient. DSPy distillation in Gate 3 can replace this with logprob-based confidence if needed.

### 6.4 Robustness

| Failure mode | Behavior |
|-------------|----------|
| Ollama down | Default to vizier-fallback, log warning |
| Malformed JSON response | Default to vizier-fallback, log warning |
| Unknown toolset name returned | Default to vizier-fallback, log warning |
| Timeout > 5s | Default to vizier-fallback, log warning |
| Confidence exactly 0.8 | Threshold is `>=`, so it uses the specific toolset |

### 6.5 Few-Shot Examples

```
"Write a blog post about tea"                           -> vizier-content
"Make a poster for DMB launch"                          -> vizier-visual
"Generate invoice for March"                            -> vizier-document
"Analyze competitor pricing data"                       -> vizier-research
"Convert this text to speech"                           -> vizier-audio
"Build a tool wrapper for X"                            -> vizier-code
"Search the knowledge base for Y"                       -> vizier-knowledge
"Send the report to client"                             -> vizier-delivery
"Full campaign for DMB: research + copy + poster"       -> vizier-fallback (multi-workflow)
```

### 6.6 Multi-Workflow Detection

If the message references 2+ workflows, classifier returns `vizier-fallback` with high confidence. The model has all tools available and orchestrates directly.

### 6.7 Integration Point

Pre-session Python script invoked by the entry point (Telegram bot handler, CLI wrapper, API endpoint) before creating the Hermes session. Not a Hermes tool. Runs before Hermes starts.

No training needed for Gate 2. Few-shot prompting on Qwen 3.5 9B is sufficient for 8-way classification. Gate 3's DSPy distillation can fine-tune later if accuracy is an issue.

**Estimated effort:** ~80 lines (classifier) + ~20 lines (integration) + tests.

## 7. Parallel Sessions (Gate 2)

Hermes's `delegate_task` is production-ready. DeerFlow patterns are absorbed as library code in `augments/deerflow/`, not as tools.

### 7.1 delegate_task Constraints (from Hermes source)

| Constraint | Value | Impact |
|-----------|-------|--------|
| Max concurrent children | 3 | Campaign decomposition must fit within 3 parallel tasks |
| Max delegation depth | 2 | Children cannot spawn grandchildren |
| Blocked tools for children | delegate_task, clarify, memory, send_message, execute_code | Children are Layer 1 + Layer 2 only |
| Child output format | `{status, summary, tokens, tool_trace, error}` | Parent receives structured JSON |

### 7.2 Orchestration Model

The model decomposes complex tasks directly. No `task_decomposer` module. Decomposition patterns documented in SOUL.md:

```markdown
When a task spans multiple workflows:
1. Identify independent sub-tasks (can run in parallel)
2. Identify dependencies (poster needs ad copy first)
3. Issue delegate_task for independent tasks simultaneously (max 3)
4. Wait for results, then issue dependent tasks
5. Call result_synthesizer to merge outputs
6. Run final pipeline (report, delivery)
```

**Example DAG:**
```
Parent receives: "Produce campaign for DMB: research + copy + poster + PDF"
Parent session: toolsets=["vizier-fallback"] (orchestration)

  -> delegate_task("research brief for DMB", toolsets=["vizier-research"])   \
  -> delegate_task("generate 3 ad copies for DMB", toolsets=["vizier-content"]) } parallel
                                                                              /
  <- wait for ad_copies result (dependency)

  -> delegate_task("design poster from ad copy", toolsets=["vizier-visual"])

  <- wait for all results

  -> result_synthesizer.merge(research, ad_copies, poster)
  -> run_pipeline("report", {sections: merged})
  -> send_telegram to deliver
```

### 7.3 result_synthesizer.py (~120 lines)

Location: `augments/deerflow/result_synthesizer.py`

- Input: list of child results (structured JSON from delegate_task)
- Output: merged deliverable structure ready for a pipeline
- Handles: missing results (child failed gracefully), partial results (child hit iteration limit), format normalization
- Parses `summary` and `tool_trace` from each child to extract observations (e.g., "child discovered DMB prefers blue tones")
- Called by the parent model after children complete

**No shared_memory.py module.** Children cannot write to shared state (memory is in DELEGATE_BLOCKED_TOOLS). Cross-agent observations come from parsing child return values, not from a separate communication channel.

**Estimated effort:** ~120 lines + tests.

## 9. OpenSpace Plugin (Gate 2)

Skill evolution running as Hermes lifecycle hooks. Core logic ported from `scouts/OpenSpace/` — extract patterns, not the runtime.

### 7.1 Plugin Registration

```yaml
# plugins/openspace/plugin.yaml
name: openspace
description: "Skill evolution - capture, fix, derive"
hooks:
  - post_tool_call
  - on_session_end
```

### 7.2 CAPTURED — Pattern Detection + Template-Based Pipeline Generation

**Hook: `post_tool_call`** — records tool call chains in SQLite (tool name, args hash, result status, session_id).

**Hook: `on_session_end`** — analyzes recorded chains. If same tool sequence appears 5+ times (configurable in `config/openspace.yaml`), generates a pipeline draft.

**Pipeline generation is template-based, NOT LLM-based.** Hermes plugins cannot make LLM calls directly. The captured tool sequence IS the pipeline. OpenSpace wraps it mechanically:

```python
# Template-generated pipeline draft (no LLM)
def run(query: str, output_format: str = "pdf") -> dict:
    step1 = call_tool("lightrag_search", {"query": query})
    step2 = call_tool("jinja2_render", {"template": "report", "context": step1})
    step3 = call_tool("typst_render", {"input_path": step2["path"]})
    return step3
```

Gate 3's code workflow improves these templates using the model's LLM. But that's model-initiated, not OpenSpace-initiated.

### 7.3 FIXED — Error-Driven Patching

**Hook: `post_tool_call` (on error)** — logs pipeline failure + input that caused it.

**Hook: `on_session_end`** — if a pipeline failed 3+ times, analyzes error patterns and generates a patched version. Archives broken version to `pipelines/_archived/`.

Patching is also template-based: common fixes (missing input field, wrong output key, timeout too short) are pattern-matched and applied mechanically.

### 7.4 DERIVED — Variant Promotion

**Hook: `on_session_end`** — compares pipeline variants by quality score (from quality gate) and token cost (from prompt logger). If a variant consistently scores higher or costs less over 10+ invocations, promotes it as the primary.

### 7.5 Supporting Modules

Location: `augments/openspace/`

| Module | Purpose | Lines |
|--------|---------|-------|
| `capturer.py` | Pattern detection logic (sequence matching, threshold checks) | ~150 |
| `fixer.py` | Error analysis + mechanical patch generation | ~120 |
| `deriver.py` | Variant comparison + promotion logic | ~100 |
| `version_dag.py` | Skill lineage tracking (parent -> child versions) | ~80 |

### 7.6 Promotion Path

Drafts go to `pipelines/_drafts/`, NOT to the active pipeline registry. Promotion:

```

  -> safety.check_skill_safety() passes
  -> quality_gate validates on sample input
  -> manifest_syncer updates _registry.yaml

```

### 9.7 Cold Start

OpenSpace produces no value until it has observed enough sessions. The capture threshold (5 identical tool sequences) means:
- First useful pipeline draft: ~50+ sessions (assuming 10% of sessions repeat the same pattern)
- Timeline: 2-4 weeks after Gate 2 deployment at normal usage
- During cold start, the system works fine — just without auto-generated pipelines

This is by design. OpenSpace learns from real production patterns, not synthetic data.

### 9.8 OpenSpace Sequence Matching Granularity

"Same tool sequence" means: **same tool names in the same order, args ignored for matching but captured for the template.** This prevents noise from identical-tool-different-input sequences while still capturing the structural pattern.

## 10. DreamSkill Plugin (Gate 2)

Memory consolidation on Qwen 3.5 9B local (zero cost). Triggered on session end.

### 10.1 Plugin Registration

```yaml
# plugins/dreamskill/plugin.yaml
name: dreamskill
description: "Memory consolidation on session end"
hooks:
  - on_session_end
```

### 10.2 Four-Phase Consolidation

```
on_session_end triggers ->
  1. DECIDE (~10ms)     - Should we consolidate?
                          Check: session had 5+ tool calls
                          OR session duration > 5 min
                          OR new patterns detected by OpenSpace
  2. GATHER (~100ms)    - Scan structlog traces from this session
                          Extract: successful patterns, client preferences,
                          tool failures, quality scores
  3. CONSOLIDATE        - Call Qwen 3.5 9B via Ollama
     (~2-5s)              Prompt: "Given these signals, produce structured diff
                          for MEMORY.md"
                          Output: {add: [...], remove: [...], update: [...]}
  4. PRUNE              - Apply diff mechanically to MEMORY.md
     (~10ms)              Keep under 200 lines
                          Remove: stale entries (not referenced in 30 days),
                          duplicates, low-value observations
```

### 10.3 Structured Diffs, Not Full Rewrites

DreamSkill produces **structured diffs**, never full MEMORY.md rewrites. Qwen could corrupt good entries during a full rewrite.

```python
# consolidator.py output format
{
    "add": ["Client DMB prefers formal tone in social posts"],
    "remove": ["entry_id_042"],          # stale, not referenced in 30 days
    "update": [{"id": "entry_037", "new_text": "DMB brand color confirmed #2E75B6"}]
}
```

The pruner applies the diff mechanically. Qwen never sees the full MEMORY.md.

### 10.4 Supporting Modules

Location: `augments/dreamskill/`

| Module | Purpose | Lines |
|--------|---------|-------|
| `consolidator.py` | Orchestrates 4 phases, calls Ollama, produces structured diff | ~100 |
| `signals.py` | Extract signals from structlog traces | ~80 |
| `pruner.py` | Apply diff to MEMORY.md, enforce 200-line limit | ~60 |

### 10.5 Diff Application Failure Handling

| Failure mode | Behavior |
|-------------|----------|
| `remove` targets entry_id that doesn't exist | Skip silently, log debug |
| `update` targets entry_id that was changed externally | Skip, log warning (manual resolution) |
| Diff would push MEMORY.md over 200 lines after additions | Apply additional pruning: oldest untouched entries removed first |
| Ollama is down | Skip consolidation entirely, log warning. Next session end tries again. |
| Qwen returns malformed diff JSON | Skip consolidation, log error with raw output |

**Estimated effort:** ~240 lines + tests.

## 11. Quality Gate Layers 3-6 (Gate 2)

Gate 1 has layers 1-2 (input validation, output verification). Gate 2 adds 4 more.

### 11.1 Layer 3: Visual QA — Structural Validation

Location: `middleware/visual_qa.py`

Validates rendered images/PDFs meet basic structural thresholds. NOT perceptual similarity (novel designs have no reference).

| Check | Method | Threshold |
|-------|--------|-----------|
| Not corrupted | PIL.Image.open() succeeds | Must open without error |
| Correct dimensions | Compare to manifest output spec | Width/height within 5% of expected |
| Not blank | Pixel variance > threshold | Variance > 100 (configurable) |
| Minimum contrast | RMS contrast calculation | Contrast ratio > 1.5:1 |
| Perceptual similarity | imagehash (ONLY for clone_converge) | Hamming distance < 15 |

**Dependencies:** pillow (already installed), imagehash (new).

### 11.2 Layer 4: Content Quality

Location: `middleware/content_quality.py`

| Check | Method | Threshold |
|-------|--------|-----------|
| Correct language | langdetect | Matches expected language (default: en) |
| No placeholder text | Regex scan | No `[TODO]`, `[STUB]`, `Lorem ipsum`, `[Generated content for:` |
| Word count | len(text.split()) | Within expected range per output type |
| Paragraph structure | Newline count / word count ratio | At least 1 paragraph break per 200 words |

**Dependencies:** langdetect (~2MB). NOT lingua-language-detector (~200MB). Same accuracy for primary language detection.

### 11.3 Layer 5: Delivery Verification

Location: `middleware/delivery_check.py`

| Channel | Success criteria |
|---------|-----------------|
| Telegram | API response status 200 + message_id returned |
| WhatsApp | httpx response status 200 |
| File output | File exists at output path with non-zero size |

### 11.4 Layer 6: Feedback Loop

Location: `middleware/feedback_loop.py`

- Records quality scores per pipeline, per client, per tool into SQLite
- Feeds into OpenSpace deriver (which pipeline variant scores best?)
- Feeds into DreamSkill signals (what quality patterns emerge?)
- No pass/fail judgment. Purely observational.

### 11.5 Updated Router

```python
def validate(data: dict, schema: dict, layer: str) -> ValidationResult:
    match layer:
        case "input":           return _validate_input(data, schema)
        case "output":          return _validate_output(data, schema)
        case "visual_qa":       return _validate_visual(data, schema)
        case "content_quality": return _validate_content(data, schema)
        case "delivery":        return _validate_delivery(data, schema)
        case "feedback":        return _record_feedback(data, schema)
```

### 11.6 Composite Quality Score

Each validation layer (1-5) contributes a score of 0 or 2:
- **0** = failed (validation errors found)
- **2** = passed (all checks clear)

**Composite score = sum of layer scores.** Range: 0-10.

| Score | Meaning | Action |
|-------|---------|--------|
| 10/10 | All 5 layers passed | Deliver immediately |
| 8/10 | 4 of 5 passed | Deliver with warning logged |
| 7/10 | Threshold (3.5 layers) | Not possible (even numbers only). Effective threshold is 8/10. |
| 6/10 | 3 of 5 passed | Hold for human review |
| 0-4/10 | Major failures | Hold + flag urgent review |

**Revised threshold:** Since layers are binary (0 or 2), the effective threshold is **8/10** (4 of 5 layers pass). Any output with 2+ layer failures is held.

Layer 6 (feedback loop) is observational and does not contribute to the score.

### 11.7 Unattended Session Rule

Composite score < 8/10 -> output held for human review in `output/_held/` with reason logged. All layer results recorded regardless of score.

**Estimated effort:** ~400 lines across 4 new middleware modules + updated router + tests.

## 12. Delivery Channels (Gate 2)

### 12.1 Telegram

Location: `scripts/delivery/telegram.py`

- Send: text messages, files (PDF, PNG), media groups
- Support: markdown formatting, caption on media, reply-to-message
- Input: chat_id, content (text or file_path), format
- Rate limiting: Telegram allows 30 msg/sec to different chats, 1 msg/sec to same chat
- Script-level retry with backoff on 429 (rate limited):

```python
async def send_with_retry(chat_id, content, max_retries=3):
    for attempt in range(max_retries):
        try:
            response = await bot.send_message(chat_id, content)
            return {"message_id": response.message_id, "status": "sent"}
        except RetryAfter as e:
            await asyncio.sleep(e.retry_after)
        except (TimedOut, NetworkError) as e:
            if attempt == max_retries - 1:
                raise
            await asyncio.sleep(2 ** attempt)
    raise DeliveryError("Max retries exceeded")
```

### 12.2 WhatsApp

Location: `scripts/delivery/whatsapp.py`

- Send: text, images, documents via WhatsApp Business Cloud API
- Input: phone_number, content, media_type
- Requires: WHATSAPP_TOKEN, WHATSAPP_PHONE_ID env vars
- Same retry pattern as Telegram (script-level, not executor-level)

### 12.3 Why Retry Lives in Delivery Scripts, Not Executor

Section 2.2 removes executor-level RetryConfig. Delivery retry is a different concern:
- Delivery targets have well-defined transient failures (rate limits, network timeouts)
- Retry semantics are channel-specific (Telegram tells you exactly how long to wait)
- Model-level retry (re-calling the tool) would lose the delivery context

Both scripts are atomic tools (manifests in `manifests/delivery/`), not pipelines. Delivery destination/message always varies.

**Estimated effort:** ~120 lines across 2 scripts + 2 manifests + tests.

## 14. DSPy Distillation Pipeline (Gate 3)

Migrate routine tasks from GPT-5.4-mini to Qwen 3.5 9B local. Dual purpose: cost reduction AND offline capability.

### 12.1 What Gets Distilled (and What Doesn't)

| Task | Distill? | Rationale |
|------|----------|-----------|

| DreamSkill memory consolidation | Already local (Qwen) | N/A |
| Content generation (creative writing) | No | Requires GPT-level reasoning |
| Template selection | Yes | Predictable, pattern-matchable |
| Quality gate content checks | Yes | Deterministic criteria |
| Tool call routing (which tool for this input) | Yes | Classification task |
| Brief -> structured outline | Yes | Structured output, learnable |
| Client voice matching | Maybe (Gate 4) | Needs per-client fine-tuning |

### 12.2 DSPy Pipeline Modules

Location: `augments/distillation/`

| Module | Purpose | Lines |
|--------|---------|-------|
| `collector.py` | Extract training examples from prompt_logger SQLite | ~100 |
| `compiler.py` | DSPy program definition + compilation to Qwen | ~150 |
| `evaluator.py` | Compare Qwen output vs GPT-5.4-mini (accuracy, latency) | ~80 |
| `deployer.py` | Swap distilled model into routing config when accuracy >= 90% | ~60 |

### 12.3 Training Flow

```
1. collector.py extracts 200+ examples from prompt_logger
   (input message -> toolset chosen -> success/fail)
2. compiler.py defines DSPy program:
   - Signature: message -> toolset
   - Optimizer: BootstrapFewShot or MIPROv2
   - Teacher: GPT-5.4-mini (via existing API)
   - Student: Qwen 3.5 9B (via Ollama)
3. compiler.py runs DSPy compilation -> optimized prompt/weights for Qwen
4. evaluator.py tests on held-out set -> accuracy report
5. If accuracy >= 90%: deployer.py updates models.yaml routing
   If < 90%: report to human, do not deploy
```

### 12.4 Incremental Distillation

Start with task classification (simplest). Add template selection, tool routing, and outline generation one at a time. Each task type gets its own DSPy program and evaluation threshold.

## 20. Risk Register

| Risk | Impact | Mitigation |
|------|--------|------------|
| Pre-classifier misroutes task | Wrong toolset, wasted turns | Confidence threshold (0.8). Below threshold -> vizier-fallback. DSPy improves accuracy in Gate 3. |
| OpenSpace generates bad pipeline drafts | Bad output if auto-promoted | Quality gate validates before promotion. Safety.py static analysis. Drafts stay in _drafts/ until validated. |
| DreamSkill corrupts MEMORY.md | Lost memory context | Structured diffs only (not full rewrites). Qwen never sees full MEMORY.md. |
| Ollama down during classification | Can't route to correct toolset | Fallback to vizier-fallback. System remains functional, just uses more tokens. |
| fal.ai cost overrun | Unexpected bills | Marked as paid in manifest. SOUL.md: prefer free tools. Usage logged by prompt_logger. |
| Unattended session produces bad output | Client receives garbage | Quality gate all 6 layers. Score < 8/10 -> held for human review. Iteration budget prevents runaway. |
| delegate_task child fails | Missing piece of complex deliverable | result_synthesizer handles partial results. Parent model can re-delegate or handle manually. |
| DSPy distillation accuracy < 90% | Can't deploy to Qwen | Don't deploy. Report to human. Continue using GPT-5.4-mini. No degradation. |
| Self-built tool has bugs | Bad tool in production | Tier 2 requires human approval for new atomic tools. Tier 1 (collapses) are based on proven patterns. |
| execute_code sandbox bypass | Security breach | AST scan catches known patterns. Audit log enables post-mortem. Gate 4 tightens based on data. |
| SOUL.md conditional loading fails | Missing behavioral rules | Hermes skills fallback: load full SOUL.md if conditional section missing. |
| Content calendar schema undefined for client | Cron job skips client | health_check cron flags clients without content_calendar config. |
| OpenSpace cold start (no historical data) | No auto-pipelines for weeks | By design. System works fine without OpenSpace. Value emerges after ~50+ sessions. |
| Cross-agent context needed but no shared memory | Sequential dependency via parent | Parent model passes relevant child observations to subsequent children. One extra turn, not a showstopper. |
| DSPy needs 200+ examples but accumulation is slow | Can't start distillation early | Lowered to 200+ examples with accuracy disclaimer. ~4 weeks at 10 sessions/day. |
| Hooks block Hermes thread during execution | DreamSkill's 2-5s Ollama call blocks | Acceptable: on_session_end fires AFTER user interaction ends. No UX impact. |
| Pipeline code contains smuggled LLM calls | Violates "no LLM in pipelines" rule | safety.py AST scan blocks openai/anthropic imports and chat completion URLs. |
